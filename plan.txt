# Project: Multi-Source Network Event & Incident Analysis Platform

ให้พัฒนา Web Application สำหรับรับ Event จากระบบ Monitoring / Management หลายประเภท เพื่อใช้เป็นศูนย์กลางสำหรับ Event Processing, Incident Tracking, Verification และ Classification

ใน Version แรกให้รองรับ PRTG Network Monitor เป็น Event Source แรก โดยรับ HTTP Notification เมื่อ Router DOWN และ UP

ในอนาคตระบบต้องสามารถรับ Event จากระบบอื่นเพิ่มเติมได้ โดยไม่ต้อง Rewrite Core Business Logic

ระบบต้องออกแบบให้ Modular, Maintainable, Extendable และไม่กระทบต่อการทำงานเดิมเมื่อเพิ่ม Event Source หรือ Analysis Flow ใหม่ในอนาคต

ห้าม Implement Feature หรือ Root Cause Flow ที่ไม่ได้ระบุไว้ใน Prompt นี้

---

# 1. My Architecture

ให้ยึด Architecture ต่อไปนี้เป็น Source of Truth

| Layer | Technology | Purpose |
|---|---|---|
| API & Backend | Django | Core auth hooks, ORM, business endpoints |
| Frontend | React + TypeScript + Vite + Tailwind CSS + shadcn/ui | Client UI, secure UX design tokens |
| Environment | Docker | รัน Application ในรูปแบบ Container |

## Architecture Constraints

ต้องปฏิบัติตามข้อกำหนดดังนี้

- Backend ต้องใช้ Django
- Frontend ต้องใช้ React
- Frontend Language ต้องใช้ TypeScript
- Build Tool ต้องใช้ Vite
- Styling ต้องใช้ Tailwind CSS
- UI Components ให้ใช้ shadcn/ui
- ระบบต้องสามารถรันผ่าน Docker
- Backend และ Frontend ต้องแยก Responsibility ชัดเจน
- Business Logic หลักต้องอยู่ฝั่ง Django Backend
- React ห้ามตัดสิน Business Logic หลัก
- ห้ามเปลี่ยน Technology Stack หลักโดยไม่ได้รับคำสั่ง
- ห้ามเพิ่ม Framework หรือ Technology ที่ทำหน้าที่ซ้ำกับ Stack ที่กำหนดไว้

หาก Requirement จำเป็นต้องมี Component เพิ่มเติม เช่น:

- Relational Database
- Background Worker
- Message Queue
- Cache
- Authentication / SSO
- Scheduler
- Event Streaming
- Monitoring Component

ให้ดำเนินการก่อน Implement ดังนี้:

1. อธิบายว่าจำเป็นเพราะอะไร
2. เสนอ Technology ที่เหมาะสม
3. อธิบายผลกระทบต่อ Architecture
4. เสนอ Alternative ถ้ามี
5. รอการอนุมัติก่อน Implement

ห้ามเพิ่ม Technology ดังกล่าวโดยอัตโนมัติ

# 8. Current Version Objective

เป้าหมายของ Version แรกคือ:

PRTG DOWN/UP

→ Normalize Event

→ Store Event

→ Track Router Incident

→ เมื่อ Routerกลับมา UP ให้ตรวจสอบ SNMP sysUpTime

→ วิเคราะห์ว่า Router มีการ Reboot หรือไม่

→ ถ้าไม่มี Evidence ว่า Reboot ให้ Classification เป็น Connectivity Loss

→ Store Evidence

→ Store Classification

→ Display Result on Dashboard

ยังไม่ต้องทำ Root Cause Analysis ต่อจาก Classification

# 10. Event Type

```text

```

และ Event Status:

```text

```

ห้ามใช้ Core Logic เช่น:

```text
if prtg_status == "UP"
```

```text
event_type == DEVICE_REACHABILITY

```

เพื่อให้ Source อื่นในอนาคตสามารถ Trigger Flow เดียวกันได้

# 11. FLOW A — Device DOWN

เมื่อ Core Event Engine ได้รับ:

```text
event_type = DEVICE_REACHABILITY
event_status = DOWN
```

ให้:

1. Validate Normalized Event
2. Identify Device
3. ตรวจสอบ Active Incident
4. ตรวจสอบ Duplicate Event
5. Create หรือ Update Incident

---

# 12. New DOWN Incident

ถ้ายังไม่มี Active Incident ที่สัมพันธ์กับ Device นี้

ให้สร้าง Incident ใหม่

บันทึกอย่างน้อย:

```text
Incident Number
Device
Status
Down Time
Last Seen
Created At
Updated At
```

Incident Status:

```text
DOWN
```

และสร้าง Event Timeline:

```text
DOWN
```

---

# 13. Duplicate DOWN

ถ้ามี Active Incident อยู่แล้ว

ห้ามสร้าง Incident ใหม่

ให้สร้าง Event:

```text
DOWN_REPEAT
```

และ Update:

```text
Last Seen
Updated At
```

ต้องรองรับ:

- Duplicate Event
- Retransmission
- Concurrent Request
- Race Condition

---

# 14. FLOW B — Device UP

เมื่อได้รับ:

```text
event_type = DEVICE_REACHABILITY
event_status = UP
```

ให้:

1. Identify Device
2. Find Active DOWN Incident
3. Create Event:

```text
UP_RECEIVED
```

4. Save Up Time
5. เปลี่ยน Status เป็น:

```text
RECOVERY_CHECK
```

6. เริ่ม SNMP Verification

---

# 15. UP Without Active Incident

ถ้าได้รับ UP แต่ไม่มี Active DOWN Incident

ห้ามสร้าง Incident ปลอม

ให้สร้าง Audit Event:

```text

```

และ Log ไว้

# 21. Case A — Uptime < 1 Hour

ถ้า:

```text
router_uptime_seconds < ROUTER_REBOOT_THRESHOLD_SECONDS
```

ให้ Classification เบื้องต้น:

```text
DEVICE_REBOOT_SUSPECTED
```

แต่ห้ามสรุปว่า Reboot เกี่ยวข้องกับ Incident ทันที

ต้องทำ Time Correlation ก่อน

---

# 22. Boot Time Correlation

สร้าง Configuration:

```text
REBOOT_TIME_TOLERANCE_SECONDS
```

Default:

```text
300
```

หรือ ±5 นาที

เปรียบเทียบ:

```text
Estimated Boot Time
```

กับ:

```text
Incident Down Time
```

ถ้า Estimated Boot Time อยู่ในช่วง:

```text
Down Time ± REBOOT_TIME_TOLERANCE_SECONDS
```

ให้:

```text
Classification:
DEVICE_REBOOT_RELATED

Confidence:
HIGH
```

---

# 23. Uptime < 1 Hour แต่ Time ไม่ Match

ถ้า Uptime < 1 Hour

แต่ Estimated Boot Time ไม่สัมพันธ์กับ Down Time

ให้:

```text
Classification:
DEVICE_REBOOT_SUSPECTED
```

Confidence:

```text
LOW
```

หรือ

```text
MEDIUM
```

ตาม Rule ที่กำหนดไว้อย่างชัดเจน

ห้ามสรุปว่า Reboot เป็น Root Cause

---

# 24. Case B — Uptime >= 1 Hour

ถ้า:

```text
router_uptime_seconds >= ROUTER_REBOOT_THRESHOLD_SECONDS
```

ให้:

```text
Classification:
CONNECTIVITY_LOSS
```

ความหมายคือ:

ไม่มี Evidence ว่า Router Reboot ในช่วง Incident

เหตุการณ์จึงควรเข้าสู่ Connectivity Analysis Flow ในอนาคต

แต่ Version นี้ยังไม่ต้อง Implement Flow ต่อไป

# 25. Important Classification Rule

ห้ามสรุป:

```text
Router Uptime > 1 Hour
=
All Links Down
```

เพราะ sysUpTime ไม่สามารถพิสูจน์ได้ว่า Link เสียทั้งหมด

ให้ใช้คำว่า:

```text
CONNECTIVITY_LOSS
```

# 26. FACT vs INFERENCE

ระบบต้องแยก FACT กับ INFERENCE

## FACT

ตัวอย่าง:

```text
Reachability DOWN
Reachability UP
SNMP sysUpTime
Down Time
Up Time
SNMP Check Time
Estimated Boot Time
```

## INFERENCE

ตัวอย่าง:

```text
DEVICE_REBOOT_RELATED
DEVICE_REBOOT_SUSPECTED
CONNECTIVITY_LOSS
UNABLE_TO_VERIFY
```

Database และ UI ต้องสามารถแสดง Evidence และ Classification แยกกัน
